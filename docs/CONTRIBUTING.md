# Правила оформления документации

Документация ведётся по принципу docs as code: правки идут через Pull Request,
как обычный код, а не редактируются напрямую в проде.

## Структура

- `docs/backend/` — методы бэкенда: атрибуты запроса/ответа, коды ошибок, Swagger
- `docs/db/` — структура таблиц, ER-диаграммы
- `docs/frontend/` — описание экранов: элементы, валидации, обработка ошибок с бэка
- Новую страницу нужно добавить и в `nav` в `mkdocs.yml`, иначе она не появится в меню сайта

## Формат страницы

- Атрибуты запросов/ответов и элементы экрана — таблицей, не списком
- Для диаграмм — PlantUML: инлайн-блок с языком `puml` (не `plantuml`) или отдельный
  `.puml`-файл рядом со страницей, подключённый как обычная markdown-картинка
  (пример — ERD в `docs/db/database.md`, ссылается на `erd.puml` рядом с собой)
- Swagger-спека подключается синтаксисом `!!swagger файл.yaml!!`, файл спецификации
  кладём в ту же папку, что и страницу

## Перед тем как открыть PR

- Проверить превью локально (`mkdocs serve`)
- CI проверяет только три вещи: орфографию (`yaspeller`), битые ссылки (`lychee`)
  и синтаксис YAML-файлов проекта (`yamllint`) — прогони их локально, если не уверен
- Технические термины, которых нет в словаре `yaspeller`, добавляй в `dictionary`
  в `.yaspellerrc`, а не игнорируй ошибку

## Pull Request

Все изменения проходят ревью перед мержем в `main`.
